# SSRF 対策仕様 (Rust 版・取得層)

作成日: 2026-11-03
状態: ドラフト (レビュー待ち)。承認までは足場・テスト・実装に着手しない。
親仕様: [rust-reboot-spec.md](../rust-reboot-spec.md) の R-10〜R-14。
参照実装: Python 版 `feedgen/core/safe_fetch.py` (main 4434803)。

## 1. 目的と脅威

公開エンドポイント `/feed?url=...` は利用者指定の URL を取得する。取得先が内部アドレスだと、サーバーを踏み台に内部サービスへ到達される。

本番 (e2) には実際に次の探査が来ており、すべて 400 で拒否された (2026-10-26〜11-03)。

| 探査の URL の対象 | 狙い |
|------------------|------|
| `169.254.169.254` | クラウドのメタデータ |
| `localhost:2019` | Caddy の管理 API |
| `127.0.0.1:9998` | ループバック上のサービス |
| `[::1]:9997` | IPv6 ループバック |
| `127.0.0.1\@8.8.8.8` | URL 解析差 (パーサごとに host の解釈が割れる) |
| (空の url) | 入力検証の穴 |

脅威は 4 種類に整理できる。
- **直接指定**: 内部アドレスや非 http(s) を直接書く。
- **URL 解析差**: 検査側と接続側で host の解釈が割れる。
- **リダイレクト**: 公開サイトから内部へ転送させる。
- **DNS リバインディング**: 検査後に名前解決の結果を内部アドレスへ変える。

## 2. 設計方針 (KISS)

1. **取得は 1 か所に集約する。** プロバイダ、フィード検出、HTML 取得はすべてこの層を通る。ここ以外から外部へ接続しない。
2. **検査は 1 つの関数に集める。** URL を受け取り、許可か拒否かを返す。
3. **名前解決は自前で 1 回だけ行い、検査済みアドレスに固定して接続する。** これで検査と接続の間に DNS が変わる余地がなくなる (リバインディング対策)。reqwest の `ClientBuilder::resolve_to_addrs` で固定できることは公式ドキュメントで確認済み。ホップごとに `Client` を作る (このツールの規模では費用は問題にならない)。独自の `dns_resolver` は、固定方式で不足が出たときだけ検討する。
4. **自動追従は使わない。** `redirect::Policy::none()` で止め、手動ループで各ホップを検査する。
5. **圧縮は扱わない。** `Accept-Encoding: identity` を送り、reqwest の圧縮 feature は有効にしない。それでも `Content-Encoding` が identity 以外で返ったら拒否する。展開器は実装しない。
6. **I/O は async (reqwest 非 blocking + tokio)。**
7. **アドレス判定は表引きで手書きする。** 標準ライブラリの `is_global` は rustc 1.98.1 でも不安定 (E0658) なので使わない。

## 3. 要件 (EARS)

### S-1 取得の入口

**Event**: 取得先 URL が渡されたとき
**Actor**: 取得層 (`SafeFetcher`)
**Response**: 次の順で検査し、1 つでも違反なら接続せずに拒否する。S-2 → S-3 → S-4 の順。
**System**: `feedgen-core::fetch`

対応メソッドは GET と HEAD のみ。それ以外は拒否する。

### S-2 URL 文字列の検査 (解析前)

**Event**: URL 文字列を受け取ったとき
**Response**: URL パーサに渡す前の**生の文字列**に対して、次を拒否する。
- 制御文字 (`0x00`〜`0x20`、`0x7f`)、空白、バックスラッシュ `\`
- 認証部 (`userinfo`) を示す `@` (authority 部分に含まれるもの)

**Why**: WHATWG 準拠のパーサは `\` を `/` として扱うため、検査側と接続側で host の解釈が割れる。e2 の探査 `127.0.0.1\@8.8.8.8` がこの型。

### S-3 URL の検査 (解析後)

**Event**: S-2 を通過したとき
**Response**: 1 回だけ `Url::parse` し、その `Url` を以後の検査と接続の両方に使う。次を拒否する。
- スキームが `http` / `https` 以外
- host がない
- host の解釈が割れるもの (S-2 の漏れを検知した場合の保険)

internationalized host (日本語ドメイン等) は、punycode に変換されたうえで S-4 を通れば許可する。

### S-4 アドレスの検査

**Event**: host が決まったとき
**Response**:
- host が IP リテラルなら、そのアドレスを検査する。リゾルバを通るかどうかに依存しない (自前で検査する)。
- host が名前なら、名前解決して全アドレスを取得する。**1 つでも非公開なら拒否する。** 非公開を除いて残りで接続する方式は取らない。
- 解決結果が空、または解決に失敗した場合も拒否する。
- 検査に通った全アドレスに固定して接続する (`resolve_to_addrs`)。

「公開アドレス」とは、次のいずれにも属さないアドレスをいう (Python の `ipaddress.is_global` と追加規則の等価、`100.64.0.0/10` も非公開)。

| 種別 | 非公開の範囲 |
|------|-------------|
| IPv4 | `0.0.0.0/8`、`10.0.0.0/8`、`100.64.0.0/10`、`127.0.0.0/8`、`169.254.0.0/16`、`172.16.0.0/12`、`192.0.0.0/24`、`192.0.2.0/24`、`192.168.0.0/16`、`198.18.0.0/15`、`198.51.100.0/24`、`203.0.113.0/24`、`224.0.0.0/4`、`240.0.0.0/4` (`255.255.255.255` を含む) |
| IPv6 の単純な範囲 | `::/128`、`::1/128`、`::/96`、`fc00::/7`、`fe80::/10`、`fec0::/10`、`ff00::/8`、`2001:db8::/32`、`100::/64` |
| IPv6 の変換系 | `64:ff9b::/96` と `64:ff9b:1::/48` (NAT64) は拒否。Teredo (`2001::/32`) は拒否。IPv4 射影 (`::ffff:0:0/96`) と 6to4 (`2002::/16`) は**埋め込まれた IPv4 を取り出して**上の IPv4 表で判定する |

ゾーン ID (`%eth0` 形式) を含むアドレスは拒否する。

### S-5 リダイレクト

**Event**: 応答が 301 / 302 / 303 / 307 / 308 で `Location` があるとき
**Response**:
- 追従せず、`Location` を `Url::join` で現在の URL に対して解決し、**S-2〜S-4 を最初からやり直す**。
- 最大 5 回まで。超えたら拒否する。
- `Location` がない場合は、その応答をそのまま返す。

### S-6 応答の上限

**Event**: 応答を受信するとき
**Response**:
- `Content-Length` が 2 MiB を超えると宣言されていれば、本文を読まずに拒否する。
- 本文はストリームで読み、累計が 2 MiB を超えた時点で打ち切って拒否する。
- 1 リクエストあたり 30 秒、リダイレクトを含む全体で 45 秒の締切を設ける。超えたら拒否する。

### S-7 圧縮

**Event**: 応答を受信したとき
**Response**: 要求に `Accept-Encoding: identity` を付ける。`Content-Encoding` が空または `identity` 以外なら拒否する。

### S-8 プロキシ

**Event**: クライアントを作るとき
**Response**: 環境変数のプロキシ設定を読まない。プロキシ経由だと、接続先がこの層から見えなくなり S-4 が働かない。

### S-9 エラー文

**Event**: 拒否するとき
**Response**:
- 「内部アドレスへの接続」「名前解決の失敗」「解決結果が空」は、**同じ文面**にする。解決したアドレスや内部の詳細を含めない。
- スキームの誤りとホストなしは、利用者の入力ミスとして文面を分けてよい。ただしアドレスは含めない。
- エラー型は `FeedError::UnsafeUrl` を追加する。API 層で 400 にマップする (R-13)。

### S-10 本番設定の安全性

**Event**: 本番のバイナリが起動するとき
**Response**: 取得層を作るコンストラクタは、アドレス判定のポリシーを引数に取らない。環境変数・設定ファイルからポリシーを変更する手段は設けない。

テスト用には、ループバックを許可するポリシーを差し込める口を `#[cfg(test)]` のコードに限って用意する。

## 4. テスト表 (RED を先に作る)

URL 文字列の検査 (S-2、S-3)。期待はすべて「拒否」。

| 入力 | 備考 |
|------|------|
| `http://127.0.0.1\@8.8.8.8/` | e2 の探査 |
| `http://user:pass@example.com/` | 認証部 |
| `http://example.com/a b` | 空白 |
| `http://exa\x00mple.com/` | 制御文字 |
| `ftp://example.com/`、`file:///etc/passwd`、`gopher://example.com/` | スキーム |
| `http:///path`、`http://` | host なし |
| (空文字列) | e2 の探査 |

アドレスの検査 (S-4)。期待は「拒否」。

| 入力 | 備考 |
|------|------|
| `http://169.254.169.254/`、`http://127.0.0.1:9998/`、`http://localhost:2019/` | e2 の探査 |
| `http://[::1]:9997/` | e2 の探査 |
| `http://2130706433/`、`http://0177.0.0.1/`、`http://0x7f.1/` | 数値表記。`url` クレートが 127.0.0.1 に正規化するかを実装時に確認し、拒否されること |
| `http://10.0.0.1/`、`http://172.16.0.1/`、`http://192.168.0.1/`、`http://100.64.0.1/` | プライベート、CGNAT |
| `http://[::ffff:127.0.0.1]/`、`http://[::ffff:10.0.0.1]/` | IPv4 射影 |
| `http://[64:ff9b::7f00:1]/` | NAT64 |
| `http://[2002:7f00:1::]/` | 6to4 に 127.0.0.1 |
| `http://[2001:0:4136:e378:8000:63bf:3fff:fdd2]/` | Teredo |
| `http://[fe80::1%25eth0]/` | ゾーン ID |
| 名前が 127.0.0.1 に解決される場合 | テスト用リゾルバで再現 |
| 名前が公開と非公開の両方に解決される場合 | 1 つでも非公開なら拒否 |
| 名前が解決できない場合、解決結果が空の場合 | 同じ文面で拒否 |

期待は「許可」。

| 入力 | 備考 |
|------|------|
| `https://example.com/` (公開アドレスに解決) | 基本形 |
| `http://8.8.8.8/` | 公開 IPv4 リテラル |
| `http://[2606:4700:4700::1111]/` | 公開 IPv6 |
| internationalized host (公開に解決) | S-3 |

リダイレクト (S-5)。

| 場面 | 期待 |
|------|------|
| 公開 → 公開 | 追従して成功 |
| 公開 → `http://127.0.0.1/`、`http://169.254.169.254/` | 拒否 |
| 公開 → 内部に解決される名前 | 拒否 |
| 公開 → 相対 `Location` | `Url::join` で解決して成功 |
| 公開 → 解釈が割れる `Location` (`\` を含む) | 拒否 |
| 6 回連続のリダイレクト | 拒否 |
| `Location` なしの 3xx | そのまま返す |

応答の上限、圧縮、プロキシ (S-6〜S-8)。ローカルサーバー 1 台で、リクエストのパスを変えて複数の関心を通す (重いテストなので数を絞る)。

| 場面 | 期待 |
|------|------|
| 2 MiB 超の `Content-Length` | 本文を読まずに拒否 |
| 宣言なしで 2 MiB 超をストリーム | 打ち切って拒否 |
| 1 バイトずつ遅く返し続ける | 全体締切で拒否 |
| 2 MiB 以内 | 成功 |
| `Content-Encoding: gzip` | 拒否 |
| チャンク転送 | 成功 |
| 要求ヘッダ | `Accept-Encoding: identity` が付く |
| `HTTP_PROXY` / `HTTPS_PROXY` を設定 | 無視され、プロキシ経由にならない |

エラー文 (S-9)。

| 場面 | 期待 |
|------|------|
| 内部アドレス、名前解決失敗、解決結果が空 | 文面が一致し、アドレスを含まない |

## 5. Python 版との差分

| 項目 | 方針 | 理由 |
|------|------|------|
| 接続直後 (TLS 前) のピア検査 | 作らない | 解決結果をその場で固定するので、接続先は検査済みアドレスに限られる |
| gzip / deflate の上限付き展開 | 作らない | identity 以外は拒否 (S-7)。展開器と爆弾対策が不要 |
| `UnicodeError` / 長すぎるラベルの個別処理 | 作らない | `Url::parse` が弾くか、名前解決が失敗して S-4 で拒否される。テストで確認する |
| API キーなどの秘匿 (Python の `_redact`) | この層ではやらない | API 層の要件 (R-13) |
| 低速応答 (slow drip) | 残す | S-6 の締切。ただしテストは 1 本に絞る |

## 6. 確認事項 (実装前に解消する)

- reqwest の `ClientBuilder::no_proxy()` が、環境変数のプロキシを確実に無効にすること (公式ドキュメントで未確認)。
- `Url::parse` が `2130706433`、`0177.0.0.1`、`0x7f.1` を 127.0.0.1 に正規化すること。
- IP リテラルの host に対して `resolve_to_addrs` が不要であること (リテラルは自前で検査し、そのまま接続する)。
- ホップごとに `Client` を作る方式で、keep-alive が効かない影響が許容範囲であること (1 リクエストあたりのホップ数は少ない想定)。
- `url` クレートと `reqwest` の現行版 (6 月の固定値は使わない)。
